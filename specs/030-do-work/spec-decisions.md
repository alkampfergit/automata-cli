# Spec Decisions: `do-work` Autonomous Orchestrator

**Feature**: `specs/030-do-work/` | **Date**: 2026-09-09

Decisions taken while specifying, with who decided and why. `[user]` marks a decision taken by the repository owner during specification; `[auto]` marks one taken by the specifying agent from the stated rationale.

| # | Decision | Source | Rationale | Rejected alternative |
|---|---|---|---|---|
| D1 | Work exists on a surface when the newest message from an authorized account is newer than the agent's newest message on that surface | [user] | This is the whole trigger: "the last message in the issue is not from the agent so the agent should answer" | Label-driven phase machine — rejected by the owner as the wrong model; the conversation already carries the state |
| D2 | Messages from accounts that are neither authorized nor the agent are ignored for detection and excluded from prompts | [user] | Anyone able to comment on a public issue would otherwise be able to command the agent | Including them as read-only context — rejected: it leaks untrusted text into the prompt |
| D3 | The pull request is inspected under the same rules as the issue | [user] | Feedback rounds happen on the PR; a loop that only watches issues stalls on the first review | Issue-only watching |
| D4 | Talk-versus-build is decided by pull-request existence; the model creates the PR when asked | [user] | Deterministic, observable in the GitHub UI, and costs no extra model call — directly serving "reducing the calls to models" | A `/implement` keyword (needs humans to remember a convention); a cheap classifier call (adds a nondeterministic model call per tick) |
| D5 | The turn instructions are prompts held in configuration; those prompts name whichever skill should be used, and this feature authors no skills | [user] | automata never has to model what a skill is: behaviour is changed by editing a file in `.automata/` with no CLI release, and the shipped defaults name no skill so the harness works with nothing installed | A `doWork.skills.*` name mapping (makes automata model a concept it does not own, when one prompt line already does it); shipping skills instead of prompts (makes the tool depend on a plugin being installed) |
| D6 | One tick processes every issue needing work, sequentially, one model run each | [user] | A cron loop must drain its queue rather than starving the second item until the next firing | One item per tick (queue drains only as fast as cron); a configurable cap as the primary mechanism (kept, but as a safety valve) |
| D7 | On the PR surface, unresolved inline threads and top-level conversation comments count; bot reviewers are ignored | [user] | Bot rounds regenerate after every push and would let the loop spin; `execute-prompt sonar` / `fix-comments` already serve them | Including bots (needs an attempt cap and still spins); inline threads only (a maintainer's "please also do X" in the PR conversation would go unanswered) |
| D8 | `do-work` is standalone; `implement-next` and `execute-prompt *` are untouched and not deprecated | [user] | Stated directly by the owner; also keeps the manual escape hatches available while `do-work` is being built | Replacing them (bigger, riskier diff, loses the escape hatches) |
| D9 | The last-run boundary is derived from the conversation, never from local state | [auto] | Must survive across VMs, containers and CI runners; already the decision taken in feature 029 | A local state file (does not survive a disposable container, which is the target environment) |
| D10 | The issue↔PR link is the GitHub closing reference, read via GraphQL `closingIssuesReferences`, and `do-work` repairs it when missing | [auto] | The link *is* the state machine (D4), so an unlinked PR would silently strand an issue in discussion forever | Body-text search for `Closes #N` (reimplements it worse and misses UI links); trusting the model to always add it (a single omission strands the issue) |
| D11 | An unresolved thread whose newest comment is the agent's own reply is answered | [auto] | Resolving is the reviewer's action; otherwise every unresolved thread retriggers a turn forever | Treating `isResolved == false` as actionable (guarantees an infinite loop) |
| D12 | New messages on both the issue and its PR produce one `pr-work` turn carrying both | [auto] | One model run with the full picture is cheaper and avoids two sessions racing on one branch | Two turns (two model calls, concurrent branch writes) |
| D13 | A merged or closed linked PR is treated as no PR | [auto] | The branch has landed or gone; the model must not push to a closed PR, and a discussion turn lets the humans say what comes next | Keeping it as a build turn (pushes to a dead branch) |
| D14 | A dirty working tree skips the item with a warning | [auto] | An unattended tool must never discard uncommitted human work | Stashing (silently hides work); resetting (destroys it) |
| D15 | The marker comment is posted before the model runs, and a failed marker skips the item | [auto] | The marker is the only record that this message was picked up; without it a crashed run answers the same message forever, and answering without it means the boundary never advances | Posting after the run (a crash re-answers); running without a marker (the loop re-triggers) |
| D16 | While one automata instance runs in a repository, no other instance starts work — an exclusive `.automata/automata.lock` taken before any state-changing call | [user] | Ticks are long (full model sessions) and cron fires on a fixed interval, so overlap is the normal case; two instances in one checkout would fight over the branch. The lock is named for automata rather than `do-work` so other long-running commands can adopt it later | No lock (concurrent pushes and branch corruption); a `do-work`-specific lock (a second format the day another command needs one); a remote lock (survives a crash, costs API calls) |
| D17 | Exit codes: 0 tick completed, 1 precondition failure, 2 ran with a failed or skipped item | [auto] | Keeps a healthy idle loop quiet while making a misconfigured loop distinguishable from a degraded one in cron mail | Always 0 (failures invisible); non-zero for "nothing to do" (cron mail on every firing) |
| D18 | The shared conversation rules are extracted into a pure module and `issueConversation.ts` becomes a wrapper with its API and tests unchanged | [auto] | `do-work` needs the identical rules over three message collections; two copies would diverge on the exact rule that stops the loop re-triggering itself | Duplicating the rules in `do-work` (correctness hazard on the most sensitive rule in the feature) |
| D19 | The executor always runs with permission prompts bypassed; isolation is documented as an operational precondition | [auto] | A cron-driven run cannot answer a permission prompt; making it optional would produce silent hangs. This matches what `execute-prompt` already does | An option to keep prompts (an unattended loop would stall on the first one) |
| D20 | `do-work` never merges a PR, never closes an issue and never pushes to the base branch | [auto] | Landing is the irreversible step and stays a human decision in this feature | Auto-merge on green (out of scope; deferred to a follow-up per T045) |
| D21 | When `do-work` first takes an issue it assigns the issue to the agent identity, before the first model run | [user] | The claim must be visible in the issue list, not only to someone who opens the thread and reads the marker comment | Relying on the marker comment alone (invisible in the issue list); a label (a second state mechanism where assignment already means exactly this) |
| D22 | Assignment is additive, skipped when already assigned, and a failure warns rather than aborting | [auto] | An issue triaged to a human must keep that assignee; assignment needs write access on the repository, and stalling the whole loop over a permissions detail that does not affect correctness would be worse than an unmarked claim | Replacing assignees (discards human triage); aborting on failure (one permissions gap stops every issue) |
| D23 | The marker comment keeps the opposite policy: a failure aborts the item | [auto] | The marker is the only record that this message was picked up. Without it the same message is answered on every later tick — a correctness failure, unlike a missing assignment | Treating both the same way (either too strict on assignment or too lax on the marker) |
| D24 | An unresolvable configured prompt fails the tick instead of falling back to the built-in default | [auto] | On an unattended loop a silent fallback changes agent behaviour invisibly; a refused tick is loud and harmless | Falling back with a warning (nobody reads cron warnings; the loop would run with the wrong instructions) |
| D25 | The process documentation is a wiki authored in-repo under `docs/wiki/`, publishable to the GitHub wiki | [user asked for a wiki; placement auto] | The repository has no conceptual documentation at all today and its `docs/<group>.md` pages are deliberately terse references. In-repo keeps the wiki reviewable in the same pull request as the behaviour it describes | The GitHub wiki as the source of truth (drifts from the code, invisible to review); a longer `docs/do-work.md` (mixes reference and narrative, breaking the documentation convention) |
| D26 | The marker is transient: deleted once the model's own answer is confirmed, updated in place when the model produced nothing | [user] | The marker is scaffolding that holds the boundary during a run; once a real answer exists it is noise in the thread, and when no answer exists it is the only thing that can tell the humans what happened | Keeping every marker (clutters the conversation the humans have to read); always deleting it (a run that answered nothing would move the boundary backwards and re-answer the same message forever) |
| D27 | "The model answered" is established by re-reading the surface, never inferred from the executor's exit code | [auto] | The two are independent: a run can exit non-zero after posting a good reply, and exit zero having posted nothing | Trusting the exit code (deletes the marker on a zero-exit silent run, causing a duplicate answer next tick) |
| D28 | An agent reply inside a review thread counts as an answer on a build turn | [auto] | Replying in the thread is the natural way to answer a line-level review; demanding a top-level comment as well would make the model post noise | Top-level comments only (the marker would be updated as "no answer" even though the reviewer was answered) |
| D29 | Updating the marker keeps its creation time, so a run that produced no answer is not retried automatically | [auto] | An unattended loop that retries a failing run on every cron firing burns model calls indefinitely on the same broken input; the updated marker text asks a human to intervene instead | Resetting the boundary to force a retry (unbounded spend on a broken input with no human in the loop) |
| D30 | The marker is posted through `gh api .../issues/{n}/comments` rather than `gh issue comment` | [auto] | Editing and deleting later require the comment id, and the creation timestamp is needed for the answer predicate; the REST response carries both, while `gh issue comment` reports neither usably. A PR is an issue in GitHub's model, so one endpoint and one edit/delete path serve both surfaces | Scraping the URL from stderr as `postComment()` does (yields no timestamp, and parsing a human-readable stderr line is fragile) |
| D31 | A failure to delete or update the marker warns without changing the item's outcome | [auto] | Neither call affects correctness once the answer exists — a stale marker is harmless because the newer answer holds the boundary | Failing the item (reports a successful turn as failed and would force exit 2 on cosmetic grounds) |
