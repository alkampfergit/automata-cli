## Planning Decisions

- **New-message detection**: The last-execution boundary is the newest issue comment authored by the configured agent account, and the command posts a marker comment as that account before invoking the AI. **Rationale**: the boundary lives with the data it describes, so it survives across machines, containers, CI runners and fresh clones — which is how a polling command is actually run — and the agent account is already required configuration for conversation filtering; `implement-next` already uses the same post-a-comment idiom. **Alternatives considered**: a local `.automata` state file (invisible to other participants, lost in ephemeral CI, desynchronises across checkouts); a reaction on the newest comment (not usefully timestamped through `gh`, trivially removed by hand); a hidden HTML marker in the comment body (the author is already unambiguous, and body parsing breaks on edits or quoting); the issue's `updatedAt` field (changes on labels, assignments and edits, so it cannot isolate a maintainer message).

- **Command placement**: Delivered as `automata execute-prompt check-issue <issue-number>` rather than a new top-level command. **Rationale**: it has exactly the shape of the existing `sonar` and `fix-comments` subcommands — gather remote context, compose a configured prompt, invoke Claude or Codex — and reuses the normalized `--with` / `--model` / `--silent` / `--push` contract from feature 028. **Alternatives considered**: a top-level `automata check-issue` (would duplicate the executor option plumbing and split a coherent group); a flag on `implement-next` (that command discovers and claims an issue from a filter, which is a different responsibility).

- **Conversation filtering**: The allowed-user/agent filter is applied uniformly, to the issue description as well as to comments; the issue number, title and URL are always included. **Rationale**: the request explicitly limits the conversation to allowed users and the agent, and applying the filter uniformly means text written by an arbitrary GitHub user never reaches the prompt as an instruction. **Alternatives considered**: always including the issue body (on a public repository anyone can open an issue, so the body is untrusted input); including non-allowed messages tagged as untrusted (scope creep, and prompt-level labelling is not a permission boundary).

- **Self-trigger safety**: Comments authored by the agent account are never counted as new messages, even when the agent account also appears in `allowedUsers`. **Rationale**: otherwise the marker comment would qualify as a new message on the next run and every invocation would trigger another one. **Alternatives considered**: rejecting a configuration that lists the agent as allowed (a hard failure is worse than doing the safe thing, and the agent's own messages legitimately belong in the conversation).

- **Timestamp comparison**: ISO-8601 UTC `createdAt` values are compared as strings, and the allowed-user message must be *strictly* newer than the last agent comment. **Rationale**: `gh` returns normalised `YYYY-MM-DDTHH:MM:SSZ`, for which lexicographic and chronological order coincide, so no date parsing is needed; strict inequality makes an exact tie resolve to a skipped run that `--force` can recover, rather than a run loop. **Alternatives considered**: comparing comment ids (`gh` returns opaque, unordered node ids); parsing to `Date` (same result, more code, silent `NaN` on malformed input).

- **Exit code for "nothing to do"**: No new message is a success — exit 0, an explanation on stdout, and no comment posted. **Rationale**: the command is built for repeated polling, so making the normal case non-zero would force every wrapper script to special-case it. **Alternatives considered**: a distinct non-zero code such as 2 (no caller in this repository reads granular exit codes, and it would break `set -e` loops on the normal case).

- **Remote-type gating**: Only an explicit `remoteType: "azdo"` is rejected, with the `docs/azdo-gap.md` pointer; an absent `remoteType` is treated as GitHub. **Rationale**: `allowedUsers` and `agentUser` are the settings that actually gate this command and both are validated with actionable errors, so demanding a third setting adds friction without safety. **Alternatives considered**: requiring `remoteType === "gh"` as `implement-next` does (that command needs the value because its discovery behaviour is remote-specific, whereas this one takes an explicit issue number).

- **Marker-comment failure handling**: If the marker comment cannot be posted, the command exits 1 before invoking the AI. **Rationale**: the marker *is* the persisted state, so running without it would leave the boundary unchanged and restart a fresh agent run on every later invocation. **Alternatives considered**: warn-and-continue, the pattern `implement-next` uses for its post-run PR updates (those warnings are cosmetic follow-ups, whereas this comment carries the deduplication guarantee).

- **Project structure**: The `gh` call (`getIssueConversation`) joins the existing GitHub wrappers in `src/config/githubService.ts` to reuse their private `spawnSync` runner, while the pure, I/O-free conversation analysis and formatting live in a new `src/github/issueConversation.ts`. **Rationale**: matches the repository's one-directory-per-domain convention (`src/claude/`, `src/codex/`, `src/git/`) and makes the detection rules unit-testable without mocking the `gh` CLI. **Alternatives considered**: putting the analysis inline in the command file (harder to test the rules directly and pushes a 150-line command module past readability); duplicating the `spawnSync` runner in the new module (violates the constitution's rule that shared logic is extracted, not duplicated).

- **Configuration storage** *(Constitution principle V deviation)*: `allowedUsers` and `agentUser` are stored in `.automata/config.json` rather than passed as flags. **Rationale**: they are stable per-repository trust settings; retyping the list of people allowed to command the agent on every invocation would make the polling use case unusable and invite copy-paste mistakes, and the file already stores directly comparable settings (`issueDiscoveryValue`, `claudeSystemPrompt`). The request also states these values belong in configuration. **Alternatives considered**: flags or environment variables only (rejected for the reasons above).
